# Security policy and threat model

This is an experimental, single-user, Linux self-hosted MCP server. It is not a hosted multi-tenant service and has not undergone an independent security audit. Report vulnerabilities privately using GitHub security advisories; never post credentials or private messages in issues.

## Protected boundaries

- History, protocol envelopes, FTS indexes and authentication keys use encrypted SQLite databases (SQLite3 Multiple Ciphers, SQLCipher-4-compatible mode). The ordinary process-lock database contains no messages or credentials.
- A 256-bit random local database key is required. Wrong keys fail closed; legacy plaintext database/auth import is unsupported.
- Automatic database backups serialize in memory then encrypt with AES-256-GCM before any backup bytes reach disk. Backups require memory proportional to database size. Large histories may exhaust memory during backup; reserve sufficient RAM.
- Bearer authentication covers MCP, health and file transfer endpoints, in addition to loopback binding and Host/Origin validation. Tokens and database keys are distinct and require owner-only file permissions.
- File sends require staging in uploads; resolved path, opened inode and hard-link checks restrict accidental secret-file exfiltration. This is not a sandbox against malicious code already running as the same OS user.
- Diagnostics omit raw failed events. Authentication and message contents are not intentionally logged. Pairing/status tool responses are sensitive and must not be published.

## What encryption does not protect

Keys generated by setup are local files. Anyone who obtains a database AND its key can decrypt it. Place keys on encrypted storage, protect your OS login, and back up keys separately. Whole-machine theft requires full-disk encryption; this application alone does not protect that scenario. Keys and plaintext are accessible to the running process and privileged malware. JavaScript cannot guarantee complete memory erasure.

Media files are plaintext in private tmpfs. They can be swapped; use encrypted swap or disable swap. Exported/copied files, core dumps, hibernation images and agent conversation logs need separate OS protection. No secure-deletion guarantee is made. Staged media is not automatically deleted on a schedule; remove it when no longer needed.

Authorized MCP clients can read history and send messages. They share one account and permission level. There is no per-tool authorization or server-side human approval dialog. Configure approval rules in your agent and confirm recipients before sending. Treat retrieved messages as untrusted content, never instructions. A model provider may see retrieved content even though storage is local.

Loopback HTTP is unencrypted local transport, protected by authentication and host checks. Never expose it remotely. WhatsApp protocol encryption does not extend to an agent after it receives decrypted messages.

## Backup and recovery

Stop the daemon before replacing database files. Preserve the current files first. To restore a `.bak` backup into a NEW encrypted database:

```bash
WHATSAPP_DB_KEY_FILE=/private/database.key node scripts/restore-backup.mjs /private/backup.bak /private/restored.sqlite
```

Restore uses private tmpfs for temporary decrypted pages, then encrypts before copying to persistent storage; encrypted swap is required for that boundary. Restore with the original key. Keep authentication and message backups identifiable and consistent; backups are not a coordinated snapshot of both databases. Never automatically replay uncertain send operations after restoring history. There is no automatic key-rotation tool in this release. Do not change the key file of an existing database.

## Release scope

Public repository contains source, synthetic tests and generic documentation only. No personal working-tree documents, existing Git history, account state, phone numbers, media, or private configuration are included. Local tests establish implementation behavior, not account availability or a guarantee against all vulnerabilities.

## Optional voice backend

Piper voice-note WAV files are created under the protected tmpfs uploads root and
removed after use. Voice models and browser profiles are local host dependencies.
Browser calling uses a separate authenticated Chromium profile with microphone
permissions and a loopback debugging endpoint. Protect that profile and endpoint
as account credentials. Call actions have no durable operation ledger; a timeout
may occur after a recipient has been reached. Never automatically redial or treat
a timeout hangup request as proof of remote termination. Mocked tests do not prove
recipient audibility. Authorization applies equally to calls and synthesized audio.
